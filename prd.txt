# Product Requirements Document (PRD)

Product Name: 会計基準 Q&A
Version: 1.0
Status: Draft
Last Updated: 2026-03-28
Owner: Product / Engineering

## 1. 背景

日本の会計基準に関する調査は、基準本文、適用指針、実務対応報告、法令、ガイドラインなど複数の一次資料を横断する必要があり、実務担当者の調査コストが高い。汎用 LLM による回答は、もっともらしいが根拠が曖昧な回答や、誤った条項参照、誤引用、過剰な探索による遅延を起こしやすい。

本プロダクトは、日本の会計基準に関する質問に対して、一次資料ベースで、出典付きかつ検証可能な回答を返す RAG チャットを提供する。

## 2. プロダクトビジョン

ユーザーが日本の会計基準について質問したときに、

- 何を根拠に答えているかが明確で
- 回答本文と参照先が整合しており
- 実務上使える粒度で
- 許容可能な時間で返る

状態を実現する。

## 3. 目的

### 3.1 ビジネス目的

- 会計・開示実務における一次調査コストを削減する
- 根拠不明な AI 回答ではなく、出典確認可能な回答体験を提供する
- 将来的に社内ナレッジ検索や専門領域 Q&A の基盤へ拡張できる形を作る

### 3.2 プロダクト目的

- 日本の会計基準に関する質問へ、一次資料に基づく正確な回答を返す
- 回答本文の各主張を番号付き参照に紐づける
- ユーザーが 1 クリックで根拠資料へ遷移できる
- 精度と速度を継続測定できる運用基盤を持つ

## 4. 対象ユーザー

### 4.1 主要ユーザー

- 経理担当者
- 開示担当者
- 会計監査対応担当者
- 会計・財務系の企画担当者

### 4.2 二次ユーザー

- 公認会計士
- 会計アドバイザリー担当者
- 法務・IR など周辺部門

### 4.3 ユーザー課題

- 会計基準の正式名称や関連文書が分からず、調査開始点が定まらない
- どの基準本文・適用指針・実務対応報告を見ればよいか分からない
- 回答をそのまま信じられず、結局 PDF を開いて再確認が必要になる
- 詳しく聞くと遅くなり、短く聞くと情報が足りない

## 5. Job To Be Done

- 日本基準の特定論点について、根拠付きで短時間に把握したい
- 回答を読んだ後、必要なら元の PDF や文書にすぐ当たりたい
- 条項指定質問では、関係ない周辺論点に寄らずピンポイントに確認したい
- 改正点や経過措置のような複合質問でも、論点を落とさず整理された回答を得たい

## 6. 成功指標

### 6.1 プロダクト KPI

- 回答評価セット pass rate: 100%
- 回答本文の無引用文率: 0%
- 回答本文の番号参照と末尾参照の不整合率: 0%
- 参照カードからの根拠資料遷移成功率: 95%以上

### 6.2 体験 KPI

- 評価セット平均応答時間: 35 秒以下を目標
- 評価セット p95 応答時間: 60 秒以下を目標
- 評価セット平均 loop 数: 5 以下を目標
- ユーザーが回答後に追加検索せず解決できる比率: 継続計測対象

### 6.3 現在のベースライン

2026-03-28 時点のローカル評価結果:

- 回答評価セット: 6/6 pass
- 平均応答時間: 47.3 秒
- p95 応答時間: 57.4 秒
- 平均 loop 数: 6.7
- 平均 retrieved tokens: 14,654

### 7.1 対象範囲

- 一次資料ベースの検索、読解、回答生成
- 回答本文の番号付き引用
- 末尾参照リストと PDF / 文書リンク
- 回答品質と速度の継続評価

### 7.2 対象資料

- ASBJ の企業会計基準、適用指針、実務対応報告
- SSBJ 基準

### 7.3 非対象

## 8. プロダクト原則

- 根拠優先: 流暢さより根拠整合性を優先する
- 一次資料優先: 二次情報ではなく、原典ベースで答える
- 検証可能性: 回答から根拠に必ず遷移できる
- 過探索抑制: 十分な根拠が揃ったら探索を打ち切る
- 誤リンク禁止: 曖昧な場合はリンクしない
- 無根拠記述禁止: 根拠がない文は出さない

## 9. 主要ユースケース

### 9.1 条項確認

例: 「企業会計基準第13号第10項では借手のリースをどのように扱いますか」

期待結果:

- 条項に近い一次資料を優先的に検索する
- 回答本文に番号付き参照を付ける
- 不必要な周辺論点を広げすぎない

### 9.2 複合論点の整理

例: 「リース会計基準の改正点と経過措置を、借手・貸手・関連基準への影響に分けて教えてください」

期待結果:

- 論点ごとに整理された回答を返す
- 詳細を落とさず、見出し単位で読みやすい構成にする

### 9.3 判断基準の説明

例: 「収益認識基準における本人と代理人の区分はどう判断しますか」

期待結果:

- 定義、判断軸、表示差異を含む
- 根拠資料に直接当たれる

## 10. 機能要件

### 10.1 質問入力

- ユーザーは日本語で質問できる
- 単一論点と複合論点の両方を受け付ける
- 会計基準番号、通称、一般的な自然文のいずれにも対応する

### 10.2 検索

- dense 検索と keyword 検索を組み合わせた hybrid retrieval を行う
- exact query と broad query で検索戦略を切り替える
- 必要に応じて query expansion と corrective query を使う
- `read_chunk` と `read_document` により、検索結果の根拠本文を精読できる
- 低価値チャンクや目次への偏りを抑制する

### 10.3 回答生成

- 回答は Markdown で返す
- 表は使わない
- 見出し以外の本文・箇条書きには必ず引用番号を付ける
- 根拠がない主張は出さない
- 直接の根拠が見つからない場合は、その旨を明示する

### 10.4 参照表示

- 回答本文の引用番号と末尾参照の番号は一致する
- 末尾参照から PDF または原文書へ遷移できる
- 参照リストは本文で実際に使ったものだけを表示する
- 文中の曖昧な用語からリンク先を推定しない

### 10.5 ストリーミング

- SSE により、調査中と回答生成中の状態を段階表示する
- 長い質問でも、進行状況が分かること

### 10.6 運用・評価

- retrieval 評価をオフラインで実行できる
- 回答品質評価をケース定義ベースで実行できる
- GitHub Actions で定期的に評価レポートを生成できる
- 評価ケースは、内容品質と効率の両方を監視できる

## 11. 非機能要件

### 11.1 正確性

- 回答は一次資料に基づくこと
- 誤った文書名リンクや誤ったページリンクを避けること
- 回答本文に出典メタ文字列をそのまま露出しないこと

### 11.2 速度

- 単純質問では過度な再検索を避ける
- exact query では keyword-first を優先する
- 長文質問でも必要以上に loop を増やさない

### 11.3 信頼性

- API の health check を提供する
- 依存サービスの一時的な揺れがあっても、評価可能な形でログを残す

### 11.4 保守性

- データ更新、index 再構築、デプロイ手順が再現可能であること
- 回答品質の regressions を検知できること

### 11.5 セキュリティ

- API キーは secret として扱う
- Cloud Run では secret manager ベースで運用する

## 12. ユーザー体験要件

- ユーザーは回答を読んだだけで要点を把握できる
- 必要なら参照カードからすぐ原文確認できる
- 回答が曖昧なときは、何が未確定かが分かる
- 回答本文に余計なページ番号や括弧書きメタ情報を出さない

## 13. リリース基準

- 回答評価セットが 100% pass
- 無引用文が残らない
- 参照番号の不整合がない
- 主要ケースで source card から原典へ遷移できる
- 週次評価 workflow が稼働し、レポートが保存される

## 14. リスク

- LLM の探索揺れにより、loop 数や token 使用量がぶれる
- exact query でも周辺論点へ広がる可能性がある
- PDF / 文書の改版によって index と chunks がずれる可能性がある
- corpus に存在しない論点について、もっともらしい補完が発生するリスクがある

## 15. リスク対応

- 評価セットで内容面と効率面の両方を継続監視する
- query rewrite と rerank を exact query / domain query 向けに個別最適化する
- 根拠不明文をサニタイズ段階で除去する
- index 再構築とデータ更新フローを手順化する

## 16. 将来ロードマップ

### 16.1 近接

## 17. Phase 6: Retrieval 強化 — 複合判断・連結・クロスリファレンス対応

### 17.1 背景

現在の retrieval は単一基準の論点検索や条項指定に強いが、以下のような実務的な質問に十分対応できていない:

- **判断検証型クエリ**: ユーザーが自身の会計処理判断を提示し、基準上の妥当性を確認する質問
  - 例: 「単体で計上される売却損（未実現損失）は連結調整で消去するべきものでないと判断。依拠：連結財務諸表に関する会計基準 第36条」
- **クロスリファレンス型クエリ**: 複数の会計基準を横断して判断を組み立てる必要がある質問
  - 例: 連結基準 + 土地再評価法 + 固定資産減損基準 を横断する処理判断
- **連結会計**: corpus に連結財務諸表に関する会計基準（企業会計基準第22号）や連結適用指針が含まれていない

### 17.2 目的

1. 判断検証型の質問に対して、ユーザーの主張を一次資料と照合し、正誤・妥当性を出典付きで回答できる
2. 複数基準を横断する質問で、関連するすべての基準を検索・引用できる
3. 連結会計、企業結合、事業分離、土地再評価など主要な未収録基準をカバーする

### 17.3 課題分析

#### A. Corpus ギャップ

現在の corpus に不足している主要基準:

| 基準 | 文書 ID | 重要度 |
|------|---------|--------|
| 連結財務諸表に関する会計基準 | 企業会計基準第22号 | 高 |
| 連結財務諸表に関する会計基準の適用指針 | 企業会計基準適用指針第22号 | 高 |
| 企業結合に関する会計基準 | 企業会計基準第21号 | 高 |
| 事業分離等に関する会計基準 | 企業会計基準第7号 | 中 |
| 持分法に関する会計基準 | 企業会計基準第16号 | 中 |
| 関連当事者の開示に関する会計基準 | 企業会計基準第11号 | 中 |
| 土地の再評価に関する法律 / 関連実務指針 | — | 中 |
| 資産除去債務に関する会計基準 | 企業会計基準第18号 | 低 |
| 会計上の変更及び誤謬の訂正に関する会計基準 | 企業会計基準第24号 | 低 |

#### B. Query 理解のギャップ

現在の query_rewrite は以下のパターンを十分に処理できない:

1. **判断検証パターン**: ユーザーが自身の会計判断を述べ、「チェックして」「妥当か」と問う形式
   - 必要な処理: 主張の分解 → 各主張に対応する基準条項の特定 → 照合
2. **暗黙のクロスリファレンス**: 質問文に複数基準が暗示されるが明示されない
   - 例: 「グループ間の土地譲渡で簿価が変わる」→ 連結基準 + 再評価
3. **長文コンテキスト付きクエリ**: 質問文自体が 200 文字を超え、処理経緯の説明を含む

#### C. Agent ループのギャップ

1. 判断検証クエリでは、通常の「情報収集 → 回答生成」ではなく「主張分解 → 各主張の根拠検索 → 照合結果の報告」というフローが必要
2. クロスリファレンスでは、1 回目の検索結果から追加検索すべき基準を推定する能力が必要
3. 現在の evidence_slots は質問文からのみ抽出されるが、判断検証では検索結果から新たなスロットが生まれうる

### 17.4 機能要件

#### FR-1: Corpus 拡充

- 上記テーブルの「高」「中」の基準を PDF / HTML で取得し、chunks.json に追加する
- 既存の process_pdfs.py / build_index.py パイプラインで処理可能であること
- source_manifest.json に新規ソースのメタデータを追加する

#### FR-2: 判断検証クエリの認識

- query_rewrite で「チェックして」「確認して」「妥当か」「正しいか」「問題ないか」等のパターンを検出する
- 判断検証と認識した場合、ユーザーの主張を構造化し、各主張に対する検索クエリを個別に生成する
- 依拠条文が明示されている場合（例: 第36条）、exact query として優先検索する

#### FR-3: クロスリファレンス検索

- 1 回目の検索結果に他の基準への言及（「○○に関する会計基準第X条参照」等）が含まれる場合、自動的に追加検索を提案する
- evidence_slots にクロスリファレンス先の基準を動的に追加する
- read_chunk / read_document で参照先基準のチャンクも取得可能にする

#### FR-4: 回答フォーマット — 判断検証型

- 判断検証クエリの回答は以下の構造とする:
  1. ユーザーの主張の要約
  2. 各主張に対する基準上の根拠と照合結果（○適切 / △要注意 / ×不適切）
  3. 追加考慮事項（あれば）
  4. 参照リスト

#### FR-5: 評価セット拡充

- 連結会計、企業結合、判断検証型の評価ケースを追加する
- クロスリファレンス型の評価ケースを追加する

### 17.5 成功指標（Phase 6 追加分）

- 連結会計関連の評価ケース pass rate: 100%
- 判断検証型クエリの評価ケース pass rate: 100%
- クロスリファレンス型クエリで関連基準を 2 つ以上引用できる比率: 90% 以上
- 既存評価ケースの regression なし

### 17.6 リスク

- corpus 拡充により index サイズが増大し、検索速度が低下する可能性
- 判断検証クエリは主張分解のステップが増えるため、loop 数・latency が増加しやすい
- クロスリファレンスの自動追加検索は、過探索の原因になりうる

### 17.7 リスク対応

- index サイズ増加の影響を embedding 再構築後にベンチマークで確認する
- 判断検証クエリの max_loops を専用に設定する（例: 12）
- クロスリファレンス追加検索は最大 2 回に制限し、過探索抑制原則を維持する

## 18. オープン事項
